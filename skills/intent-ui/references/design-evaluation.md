# 设计评估方法

目录：方法选取、批评与评审、启发式评估、认知走查、无障碍验收基线、评审意见协议、体验度量、设计 QA。本文件只回答"用什么方法评估、如何记录结论"；验收哪些行为由 [交付与检查](delivery-and-review.md) 的验收选取决定，能力取舍见 [能力判断](capability-decision.md)，组件行为规则见 [组件交互设计语言](component-interaction-language.md)。方法骨架取自 NN/g 与 W3C 的公开方法论并按后台场景适配，不是一份联合标准；方法选取表、评审意见协议与门槛约定为本 Skill 扩展。全部外部来源的链接、参考日期与适配边界登记在 [流程、评估与设计系统来源](process-sources.md)，正文只给结论与短引用。

## 方法选取

评估方法不默认全部执行。按对象所处阶段与所需证据选取；省略某项时记录重新评估条件。

| 方法 | 何时必需 | 可省略或降级 | 重新评估条件 |
| --- | --- | --- | --- |
| 设计批评 | 方案成形中、存在方向分歧 | 范围明确的小修改直接进评审 | 修改引出新的方向争议 |
| 启发式评估 | 交付节点前系统性查漏，或无法接触真实用户 | 单点微调只对照涉及条目 | 同类问题反馈反复出现、界面结构大改 |
| 认知走查 | 免培训、靠探索完成的首次使用流程 | 有培训与文档保障的高频内部操作 | 新角色接入、支持工单反映用户无法自行完成 |
| 无障碍验收 | 新页面、新组件或交互行为变更 | 纯文案改动降级为对比度与 label 抽查 | 焦点管理、组件结构或浮层层级变化 |
| 体验度量 | 改版需要前后对比或结论存在争议 | 无基线数据的一次性小改动 | 改动触及核心任务流程 |
| 设计 QA | 存在批准稿、token、组件库等权威参照物的实现核对 | 无视觉交付物的纯逻辑变更 | 参照物更新、token 或组件库升级 |

## 批评与评审是两种模式

| 维度 | 批评 Critique | 评审 Review |
| --- | --- | --- |
| 时机 | 设计进行中 | 交付或里程碑节点 |
| 对照物 | 本次设计目标 | 明确清单：启发式、规范条款、验收条目 |
| 结论 | 不做通过判定，只产出改进方向 | 分级意见与签核结论 |
| 输出 | 带 owner 的行动项 | 按评审意见协议记录的意见清单 |

- 批评议程（人类团队参与时）：主讲人说明目标、阶段与期望的反馈类型 → 参与者静默浏览形成独立意见 → 结构化反馈轮 → 主讲人回应 → 记录带 owner 的行动项。主讲人提供上下文、不逐条辩护；反馈者区分阻断性疑虑与一般建议。
- 评审议程：声明对照清单与范围 → 逐条检查 → 按评审意见协议记录 → 给出通过、有条件通过或不通过的签核结论。
- AI 或其他单评估者执行时：省略会议环节，按下方反馈规则直接产出对应输出（批评为带 owner 的行动项，评审按评审意见协议记录），并在结论中声明单评估者局限；评审产生"明显影响效率或可靠性"及以上级别意见，或签核结论存在争议时，签核前提请人工复核。

反馈规则，两种模式通用：

- 反馈锚定既定目标而非个人品味："该布局与'减少录入步骤'的目标冲突"成立，"我不喜欢"不成立。
- 证据不足的疑虑用提问表达，不预设结论。
- 指出问题及其后果，问题描述不夹带替代方案，最终改法由设计 owner 决定；评审记录可在"最小修正"字段给修复方向参考（见评审意见协议）。

议程结构综合 NN/g 与 Figma 公开实践提炼，不是官方统一流程。

## 启发式评估

对照 Nielsen 十条清单逐条检查。清单与严重性量表属 NN/g 体系，引用时不升级为法律或 W3C 要求。

| # | 启发式 |
| --- | --- |
| 1 | 系统状态可见性 |
| 2 | 系统与真实世界匹配 |
| 3 | 用户控制与自由（撤销、退出） |
| 4 | 一致性与标准 |
| 5 | 错误预防 |
| 6 | 识别而非回忆 |
| 7 | 使用的灵活性与效率 |
| 8 | 美观与极简设计 |
| 9 | 帮助用户识别、诊断并从错误中恢复 |
| 10 | 帮助与文档 |

- 每名评估者过界面两遍：先走整体流程，再逐元素对照条目。人类团队评估时各自独立评估后汇总去重，不在讨论后补记；单评估者（含 AI 自评）沿用两遍法，逐条目独立记录后合并评级，并按下文声明局限。
- 严重性在问题合并后统一评级，由频率、影响、持续性三因素综合决定。
- 每条问题记录：违反条目编号 + 位置（页面、组件或截图）+ 问题描述 + 严重性评分；问题描述写问题本身，不写成解决方案。

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| 0 | 非问题 | 剔除 |
| 1 | 外观性 | 有余力才修 |
| 2 | 次要 | 低优先级 |
| 3 | 主要 | 高优先级修复 |
| 4 | 灾难性 | 发布前必须修复 |

交付门槛（本 Skill 在 NN/g 判断上的收紧约定）：存在未闭环的 3-4 级问题即阻断交付；闭环指修复并复验，或由负责人显式接受风险并登记例外台账。

局限随结论一并声明：NN/g 的评级可靠性建立在多名评估者取均值上，单一评估者（包括单次 AI 自评）的评分波动大，只作排序与门槛判断，不当精确测量；启发式评估会产生真实用户不受影响的误报，不能替代可用性测试。

## 认知走查

适用条件：用户免培训、靠探索完成的首次使用流程，例如自助开通、低频配置页。协议四步：

1. 选代表性新手任务，写出完成任务的 happy path 动作序列。
2. 对每一步回答四问：用户会试图达成正确的目标吗；会注意到正确操作可用吗；会把该操作与目标关联起来吗；执行后能看到任务在推进吗。
3. 任何一问给不出可信的"是"，写一条失败故事：在哪一步、用户会怎么想、为什么走错。
4. 失败故事转为设计修改项，按评审意见协议记录。

四问表述综合 NN/g 与 Userfocus 版本提炼，不是官方统一文本。

## 无障碍验收基线

验收基线锚定 WCAG 2.2 AA，不以 WCAG 3 为验收基线；标准现状与 EN 301 549 的时效论证见 [流程、评估与设计系统来源](process-sources.md)。设计期页面交互底线见 [状态与业务流程](states-and-workflows.md)，本节只规定验收方法。WCAG 2.2 新增条款中与后台系统最相关的五条：

| 条款 | 级别 | 后台验收点 |
| --- | --- | --- |
| 2.4.11 Focus Not Obscured (Minimum) | AA | 粘性表头、固定侧栏、浮层不完全遮挡键盘焦点所在元素 |
| 2.5.7 Dragging Movements | AA | 拖拽排序、看板移动提供非拖拽替代操作 |
| 2.5.8 Target Size (Minimum) | AA | 交互目标不小于 24×24 CSS px 或有等效间距；重点查表格行内图标按钮 |
| 3.2.6 Consistent Help | A | 帮助入口跨页面位置一致 |
| 3.3.7 Redundant Entry | A | 同一流程不要求重复录入已填信息，提供回填或选择 |

24×24 与下文对比度数值是 WCAG 条款值，只在核对 WCAG 符合性时按原文适用，不挪作通用设计阈值。

最小必查清单（按 WCAG 2.2 AA 条款整理的实务抽查项，通过不构成合规认证）：

- 键盘可达、焦点与弹层管理、辅助技术感知、label 与错误说明等行为底线，按 [状态与业务流程](states-and-workflows.md) 与 [组件交互设计语言](component-interaction-language.md) 对应条目逐项核对，本节不复述。
- 文本对比 4.5:1；UI 组件与图形 3:1。
- 目标尺寸与拖拽替代按上表核对。

组件级验收不另造清单：从组件对应 APG 模式的 Keyboard Interaction 表与 Roles, States, and Properties 表逐行生成用例；引用与差异处理见 [组件来源与差异处理](component-sources.md)。

大型系统按 WCAG-EM 五步抽样，不逐页全检：定范围与目标等级 → 探索关键页面与技术 → 结构化样本（通用页 + 关键功能 + 各内容类型）加随机样本 → 逐条审计 → 报告。WCAG-EM 是评估方法论，不新增符合性要求。

自动化扫描只覆盖部分条款，通过扫描不等于通过验收；必须补充手动键盘走查与读屏抽测。

## 评审意见协议

评审模式下每条意见按四要素记录，缺要素的意见退回补全。该协议为本 Skill 扩展。

| 要素 | 取值 |
| --- | --- |
| 维度 | 流程、交互、视觉、文案、无障碍、一致性 |
| 级别 | 沿用现有系统评审三级：阻断或高影响（不解决不签核）、明显影响效率或可靠性（可签核但限期闭环）、可选优化（有收益不强制）；另设疑问（信息不足，澄清后归入前三级） |
| 依据 | 设计目标、规范条款、启发式编号或 WCAG SC，必须可追溯 |
| owner 与结论 | 负责人及处理结果 |

- 启发式 4 级问题默认归"阻断或高影响"，3 级默认归"明显影响效率或可靠性"，最终级别按本项目实际影响判断。
- 发现结构与证据要求沿用 [交付与检查](delivery-and-review.md) 的现有系统评审格式，其中"严重程度"字段由本协议"级别"承载，不并存两套词汇。
- "最小修正"是发现记录中独立于问题描述的字段，只给修复方向参考，不构成对 owner 的强制改法；"不强加替代方案"约束问题描述与反馈表达，不豁免该字段。批评模式无签核记录，不产出该字段。

## 体验度量

适用条件：改版需要前后对比，或评审结论存在争议需要行为证据。后台默认度量集如下，属多来源综合提炼，不是官方套餐：

| 指标 | 用法 |
| --- | --- |
| 任务成功率 | 先定义可判定的成功判据（二元或分级），同一任务集前后对比 |
| 任务时长 | 同一任务集改版前后对比，显著变长按效率回退处理，判定方式见下方基准对比规则 |
| 错误率 | 操作错误与求助次数一并记录 |
| SUS | 10 题 0-100 感知可用性量表；均值基准 68 属 SUS 研究体系数值（MeasuringU），不是本 Skill 阈值 |
| HEART | 后台优先 Task success 与 Adoption，按 Goals-Signals-Metrics 从目标推导指标 |

- 效率工具不把停留时长、页面浏览量等 Engagement 指标当正向目标；时长上升先怀疑效率回退，再考虑其他解释。
- 度量作门槛的方式是基准对比：改版前后用同一任务集、同一判据测量，关键指标回退则评审不通过；不设统一的绝对达标数值。

## 设计 QA

适用条件：实现与设计交付物的核对阶段。与 [交付与检查](delivery-and-review.md) 的分工：验收选取表决定"验收哪些行为"，本节决定"对照什么、怎么记录"。

- 对照权威参照物逐项核对：批准稿、design token、组件库文档；凭记忆或品味判断无效，参照物缺失先补参照物，不边猜边验。
- 重点检查"没人画过的状态"：空态、加载、错误、超长与极限内容、disabled 与 focus 态、断点之间的宽度；已画过的主流程按参照物常规核对。
- 每项记录三态：pass、fix（必须指派 owner）、accepted-risk（记录接受理由）；禁止无结论的"看起来没问题"。
- accepted-risk 登记例外台账并注明复查条件（参照物更新、下一版本回归），不随签核一笔勾销。三态记录与例外台账为本 Skill 扩展，QA 检查维度综合业界公开清单提炼。
