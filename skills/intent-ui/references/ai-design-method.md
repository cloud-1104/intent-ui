# AI 设计思路

适用条件：AI（含使用本 Skill 的模型自身）起草界面、编写界面代码、驱动 prompt-to-UI 工具或组织多 agent 设计流程时读取。本文件属方法层，规定执行设计时的思考与自律方式；能力取舍见 [能力判断](capability-decision.md)，组件语义与键盘焦点见 [组件交互设计语言](component-interaction-language.md)，交付模板与验收选取见 [交付与检查](delivery-and-review.md)。除文内标注来源的结论外，规则为多来源综合提炼与本 Skill 扩展，不是任何单一工具的官方标准。

目录：生成前自校准、设计上下文分层与降级、生成与检查的边界、失败模式与防护、假设管理与自评边界、多 agent 协作分工、状态完备性硬门槛。

## 生成前自校准

模型默认输出趋向训练数据中的高概率通用设计：不加约束时会收敛到同一批“安全”选择，产出千篇一律的界面。开工先承认这一倾向，把默认产出当作需要主动抵消的起点，不当作中立基准。依据：[Anthropic：通过 Skills 改进前端设计](https://claude.com/resources/articles/improving-frontend-design-through-skills)对分布收敛的描述；下列三段结构为对该文方法的综合提炼与通用化（从字体、颜色等具体项泛化到任意设计决策），非本 Skill 原创。

为项目撰写反收敛规则时，每条按三段写：

| 段 | 要求 |
| --- | --- |
| 禁用默认 | 点名模型惯性会给出的具体选择，说明为何不适用本项目 |
| 替代方向 | 给出可执行的选择空间，不锁定唯一答案 |
| 防二次收敛 | 声明替代项不是新的标准答案，防止所有产出收敛到同一替代 |

- 项目或设计系统已有明确风格资产时 → 直接服从资产；自校准只用于资产未覆盖的空白。
- 任何自校准规则 → 保持恰当抽象高度：不硬编码 hex、px、字体名等具体值（值属于 design tokens 层），也不写“要有高级感”这类无法执行的口号；每条规则都要能映射到可实现、可检查的产出。
- 可省略：一次性低风险草图或纯探索可跳过书面自校准；产出一旦进入评审或实现，先补齐再推进。

## 设计上下文分层与降级

开工前盘点五层设计上下文。分层口径为本 Skill 扩展，用于统一“缺什么、先补什么”的判断；缺层不阻塞开工，但降级动作与重新评估条件必须随产物记录。token 的架构、命名与组件规范细则见 [设计系统与令牌规范](design-system-spec.md)。

| 层 | 提供什么 | 缺失时的降级动作 |
| --- | --- | --- |
| 设计稿或截图 | 目标形态与布局证据 | 用结构化 brief 文字描述形态并标注为假设，首稿后尽早补对照 |
| 组件映射 | 设计元素到代码组件的对应 | 先建立映射表再写代码；对应不上的元素列待确认，不猜实现 |
| design tokens | 颜色、间距、字号等已解析值 | 先定义 token（命名、值、用途）再写样式，不先写裸值 |
| 组件库文档 | 现有组件的 props、状态与约束 | 以源码或类型定义核对；核对不到的用法不使用 |
| 书面设计决策 | 风格取舍、交互约定、禁用项 | 从现有界面归纳临时约定并声明为假设，交人确认后沉淀 |

- 写样式时 → 只引用已登记 token；缺 token 的固定顺序是“先建 token、再写样式”，不许先写裸值等以后替换。
- 任何一层 → 不得靠发明补齐：设计系统中不存在的 token、组件变体、props 一律不虚构；确有需要时作为新增提案走待确认，不直接进产物。
- 每次降级 → 记录可复查的重新评估条件（如“拿到正式设计稿后复核临时组件映射”），不把临时约定固化成事实标准。

## 生成与检查的边界

行业经验把 AI 生成定位在前段：“70% 问题”指 AI 快速完成大部分首稿，剩余部分——可靠性、无障碍、设计系统对齐、真实数据边界——仍需专家判断。70% 是经验命名不是实测比例，不得当作验收指标。依据：Addy Osmani 提出的 [“70% problem”](https://addyo.substack.com/p/the-70-problem-hard-truths-about)与 [NN/g 对 AI 原型“远看可观、细节不足”的实测结论](https://www.nngroup.com/articles/ai-prototyping/)。

- AI 生成的职责 → 探索方向、产出首稿、批量给出备选；产物默认是待验证草稿，不是可直接合并的成品。
- 剩余部分的职责 → 不交给“再生成一次”解决，由规则化检查兜住：状态核对见本文末节，验收选取见 [交付与检查](delivery-and-review.md)，组件语义核对见 [组件交互设计语言](component-interaction-language.md)。
- 输入门槛 → 模糊 prompt 视为不合格输入。生成前 brief 至少包含：目标任务与用户、涉及组件、必须遵守的约束（token、无障碍、既有规范）、引用的工件（设计稿、现有页面、数据样例）；缺项先补 brief，不靠生成后猜测补救。
- 提高具体度 → 能引用工件就不用纯文字转述。NN/g 把 prompt 具体度分为宽泛文本、详细文本、文本加设计工件、改版提示四级，具体度越高产出越可用；该分级属 NN/g 测试体系，作参考坐标。
- 可省略：探索期对比多方向时 brief 可以较粗；进入聚焦精修前必须补成结构化 brief。

## 失败模式与防护

下表为多来源综合提炼的五类高频失败模式，不是任何工具的官方清单。防护必须在生成循环内执行：事后评审的节奏跟不上生成速度，检查须前移到生成时。

| 失败模式 | 典型表现 | 生成循环内防护 |
| --- | --- | --- |
| 千篇一律 | 收敛到高概率通用样式 | 执行“生成前自校准”的禁用默认＋替代方向 |
| token/样式幻觉 | 发明系统中不存在的颜色、间距、变体 | 只引用已登记 token；diff 中逐项排查新增裸值与未注册用法 |
| 状态遗漏 | “看似隐含”的 hover、focus、error、empty、loading、权限态被跳过 | 交付前过“状态完备性硬门槛”，逐项核对不凭印象 |
| 无障碍缺失 | ARIA、键盘、焦点因视觉不可见被忽略 | 按所用组件核对必需语义与键盘流程，见 [组件交互设计语言](component-interaction-language.md) |
| 漂移复利 | 单次例外被后续生成复制引用，错误级联 | 例外显式登记原因与回收条件，不静默保留 |

- 单次生成或修改 → 只做一个声明范围内的改动；范围外的“顺手优化”拆成独立请求，否则 diff 无法排查。
- 每次产出 → 对照 diff 排查发明样式与越界改动；发现即回退或登记，不以“下轮再清”拖延。
- 已登记例外 → 是待回收的债务不是新基线；再次引用前先核对回收条件是否已触发。

## 假设管理与自评边界

- 任何设计陈述 → 标明属于证据（可指认的需求、截图、源码或来源文档）、假设（写明推断依据）或待确认（影响关键决策且证据不足）；待确认的定义与处置沿用 SKILL.md 能力矩阵的同名状态，不另立口径。
- 生成产物“看起来合理” → 不构成证据升级；截图与首稿只证明可见形态，不证明行为、权限或数据边界。
- AI 自评与互评 → 只能作人审前初筛：实证研究显示 LLM 在启发式评估的查全率与抽象判断上不及人类专家。依据：[GPT-4o 与人类专家对比研究](https://arxiv.org/html/2506.16345)、[Microsoft UXR 的结论](https://medium.com/uxr-microsoft/why-ai-tools-are-not-ready-to-replace-human-heuristic-evaluations-yet-e56a143c0967)。
- 自评维度 → 可沿用 [NN/g 四维框架](https://www.nngroup.com/articles/testing-ai-methodology/)：目标一致性、概念质量、视觉设计、交互与可用性；该框架属 NN/g 评估体系，引用时注明，不当作本 Skill 原创。
- 初筛通过的表述 → 只能写“初筛未发现问题”，不能写“已通过评审”；人审前产物保持草稿状态。

## 多 agent 协作分工

条件必需：多个 agent 协同完成设计任务时适用。单 agent 不必虚构角色，但评审仍须与生成分开执行、分开记录。分工模式为多来源实践综合，不是某一编排框架的规定。

| 角色 | 职责 | 边界 |
| --- | --- | --- |
| 规划 | 拆解需求、定范围与验收依据、分派任务 | 不直接产出设计或代码 |
| 生成 | 按 brief 产出设计或代码，持有产物写权限 | 不自行判定通过，不扩大改动范围 |
| 评审 | 持独立验收清单检查产物并出报告 | 只出报告不改产物，避免自我评审偏差 |
| 规范维护（可选） | 维护项目设计规范与例外登记 | 不介入单次产物的生成与评审结论 |

- 验收清单 → 生成开始前由规划角色依据 [交付与检查](delivery-and-review.md) 的验收选取裁剪固定；不由生成者事后自拟。
- 评审手段 → 按产物形态选择：代码核对 diff 与声明的契约；界面在真实渲染下核对状态与交互（截图或浏览器验证），不只读源码下结论。
- 人的介入点 → 方向选择（多方案收敛为一）与合并门槛（进入主干或对外交付）由人决策，agent 不自行放行。
- 可省略：单人小改动不必搭建完整流水线；涉及公共规范、跨模块影响或不可逆操作时，重新启用角色分离。

## 状态完备性硬门槛

条件必需：任何界面产物在提交评审、合并或声明完成前执行。本门槛针对“状态遗漏”失败模式；清单项为多来源共识，核对动作与结论口径为本 Skill 扩展。各状态的语义与呈现规则见 [状态与业务流程](states-and-workflows.md)，此处只规定核对动作本身。

- 交互与请求状态 → loading、empty、error、success、disabled、focus、权限不足逐项给出结论：已实现、确认不适用（写明原因）或登记缺口；不允许留空。
- 内容边界 → 空内容、超长内容、错误内容分别核对呈现：截断、换行、占位与报错行为可观察。
- 响应式断点 → 核对规则归属 [状态与业务流程](states-and-workflows.md) 的可访问性与响应式一节，交付前与本门槛一并执行，此处不重复规定断点细则。
- “不适用”判定 → 必须可复查：写明依据（如“纯静态说明页无网络请求，无 loading 态”），条件变化时重新核对。
- 核对结果 → 随交付物一并给出；未附核对结果的界面交付视为未完成，不以“常规状态都有”带过。
