# 设计工作流程

本文件定义一次 UI 设计工作的阶段编排与交付物链，在开始新设计任务、决定流程走多深、确定产出哪些交付物或检查产出链完整性时读取。能力取舍规则见 [能力判断](capability-decision.md)，组件行为见 [组件交互设计语言](component-interaction-language.md)，交付格式模板与验收选取见 [交付与检查](delivery-and-review.md)，本文不重复其内容。

四阶段骨架是对 ISO 9241-210 四核心活动与 Design Council Double Diamond 等模型的综合提炼，不是任何单一模型的官方流程，也不存在这些模型的联合标准；标注“本 Skill 扩展”的规则为自有扩展。

## 统一骨架：理解 → 定义 → 方案 → 验证

四阶段构成迭代环而非单行线。[ISO 9241-210](https://webstore.ansi.org/preview-pages/ISO/preview_ISO+9241-210-2019.pdf) 规定迭代持续到“设计方案满足已说明的用户需求”为止，并要求设计由评估驱动；[Double Diamond](https://www.designcouncil.org.uk/resources/framework-for-innovation/) 明确允许从任意阶段回退。

| 阶段 | 进入条件 | 核心活动 | 输出 | 推进门槛（进入下一阶段的证据） | 回退触发 |
| --- | --- | --- | --- | --- | --- |
| 理解 | 接到任务，或回退要求重新理解 | 按 SKILL.md“建立业务上下文”收集任务、数据、状态、权限与规模证据，区分事实与假设 | 使用情境说明＋假设清单 | 影响关键决策的信息已有证据或已标注待确认 | 任一后续阶段发现情境与事实不符 |
| 定义 | 使用情境说明存在 | 收敛问题，不展开方案 | 问题陈述：用户＋场景＋待完成任务＋期望结果＋成功信号 | 对要解决的问题达成共识；方向性任务需用户确认问题陈述 | 方案阶段发现问题过宽、过窄或基于错误假设 |
| 方案 | 问题陈述已收敛 | 发散候选方向，按[能力判断](capability-decision.md)收敛范围，产出交付物链 | 能力矩阵、用户流程/wireflow、全状态屏幕定义、规格 | 方案能对照问题陈述逐条核对，交付物质量判据达标 | 发散不出可行方向回定义；出现新的关键情境信息回理解 |
| 验证 | 方案可对照需求核对 | 对照问题陈述自评估，执行 SKILL.md 交付前检查，产出验收清单 | 评估结论、验收清单、未决项 | 对照已说明的需求评估通过，验收条目可判定 | 评估未通过，回流到产生缺陷的阶段 |

- 评估未通过 → 回到产生缺陷的活动修正，不在验证阶段改写措辞掩盖（ISO 9241-210“评估驱动”原则）。
- 回退不是失败：验证阶段的新认知回流到理解或定义属正常机制；回退时记录触发原因（记录要求为本 Skill 扩展）。
- 退出条件是“满足已说明的用户需求”，不是“阶段都走过一遍”或“轮数用完”。

## 发散与收敛纪律

交替节奏依据 Double Diamond：发散扩充候选，收敛裁剪定稿；显式阶段标记为本 Skill 扩展。

- 产出任何阶段结论前 → 声明当前处于发散还是收敛。
- 问题陈述未收敛 → 禁止进入方案发散，不以“顺手给个方案”替代定义。
- 处于发散 → 不过早定稿；方向性问题至少给出相互竞争的多个候选，不因出现第一个可行方案就停止。
- 处于收敛 → 不引入新方向；新想法记录为下一轮输入，或显式触发回退。
- 存在多个候选 → 先独立生成互相竞争的草案，再按统一准则比选并写明每个落选方向的淘汰理由，最终由用户拍板。该机制提炼自 [GV Design Sprint](https://www.gv.com/sprint/) 的独立草图与结构化决策（反群体思维），为可选手段；五天日程、5 名用户访谈是该方法自身设定，不是通用门槛。
- 任何阶段 → 禁止用高保真细节为未验证方向背书；少量示例不得写成普遍结论。

## 流程裁剪

依据 NN/g [Design Process Isn't Dead, It's Compressed](https://www.nngroup.com/articles/design-process-isnt-dead/)：专家压缩流程而非丢弃流程。压缩的是各阶段深度与文档重量；无论路径多短，输出都要能回答“问题是什么、为什么是这个方案、怎么判定完成”。

| 任务特征 | 路径 | 保留义务 |
| --- | --- | --- |
| 问题模糊、方向未定，或进入新用户群 | 全流程 | 完整理解与定义；问题陈述经确认后才进方案 |
| 问题已明确，但方案空间大或操作风险高（删除、审批、资金、权限） | 压缩流程 | 理解与定义做轻量核对；重心放在多方案比选与验证 |
| 问题与方案都明确的小改动，沿用既有模式 | 直通规则层 | 引用既有问题陈述与流程，按规则层文件直接产出；验证不可省 |

输出中声明所走路径、跳过的阶段及理由（本 Skill 扩展）。对应 SKILL.md 五种工作方式：

| 工作方式 | 默认路径 | 流程重心 |
| --- | --- | --- |
| 制定通用规范 | 压缩流程 | 理解阶段收集适用范围与目标读者，不虚构具体业务情境；重心在定义条件规则与验证口径一致 |
| 设计具体模块 | 全流程；情境已有证据时压缩 | 理解与定义必做；交付物链完整产出或逐件引用 |
| 设计或审查组件行为 | 压缩流程 | 问题陈述通常由模块层给出；重心在方案比选与行为验收 |
| 审查现有后台 | 从验证进入 | 先重建该任务的理解与定义，再对照评估；发现按阶段回流 |
| 实现或修复交互 | 直通规则层 | 只实现已验证范围；未经定义与验证的新需求不得在实现中顺手加入（提炼自 SVPG 持续发现与交付） |

## 最小可行交付物链（后台场景）

链条：问题陈述 → 用户流程/wireflow → 全状态屏幕定义 → 规格 → 验收。统一省略判定问句：**该交付物要消除的不确定性是否已消除？** 已消除则引用既有结论并记录出处，不是留空（依据 [Lean IA](https://jeffgothelf.com/blog/lean-ia-getting-out-of-the-deliverables-business/)：交付物只为回答未决问题而存在）。

| 交付物 | 消除的不确定性 | 质量判据 | 省略判定与重新评估条件 |
| --- | --- | --- | --- |
| 问题陈述（JTBD 式） | 为谁、完成什么任务、期望什么结果 | 聚焦要达成的结果而非功能清单；含可观察的成功信号 | 既有研究已覆盖本任务时引用一句话版本；目标用户或任务变化时重做 |
| 用户流程 / wireflow | 用户如何到达目标，流程逻辑是否会走样 | 一图一目标一角色；入口明确；每个决策分支有标签；含失败与异常分支；有明确终点 | 流程未变且只改单屏内交互时引用既有流程；涉及新实体或新导航入口必须新做 |
| 全状态屏幕定义 | 界面是否会走样 | 引用 token 与组件名而非裸值；真实内容并覆盖空、超长、错误三类；枚举适用的数据与交互状态（清单见[状态与业务流程](states-and-workflows.md)） | 不可缺位；状态未枚举视为定义不完整，不得进入实现 |
| 规格 | 实现者是否获得全部必需信息 | 六要素齐备并单列范围内外边界（见下节） | 前序交付物已承载全部信息且读者相同时可合并承载，六要素仍须逐项出现 |
| 验收 | 完成与否是否可判定 | 每条可判定、可观察；禁止主观词；视觉条目引用 token 与所属体系的可测阈值；格式与选取见[交付与检查](delivery-and-review.md) | 不可缺位；写不出可判定条目说明定义或方案未收敛，按回退处理 |

- 流程、界面、判定标准是实现走样的三个来源，三者必须各有承载物：可引用既有物，不可没有。此为多来源综合提炼，不是单一来源原文。
- 旅程图、站点地图、卡片分类、独立视觉探索是按需追加项 → 仅在导航结构变化、进入新用户群或建立新视觉语言时产出，平时不默认制作。
- 保真度按要验证的问题选择 → 验证结构与流程用低保真；验证可用性、视觉与文案用高保真；验证交互行为用可交互原型；行为已由既有组件库定义时，用静态稿加组件引用代替原型（提炼自 NN/g 保真度三轴）。
- 每份交付物声明目标读者 → 给干系人与给实现者的不是同一份。
- 接收方是 AI 编码代理时 → 补机器可读上下文：design token、组件到代码的映射、书面设计决策；只给截图会导致硬编码裸值与重复造组件（2024-2026 行业案例的提炼，非标准）。
- 后台系统的结构层优先用 wireflow：页面少、状态多时，单独的线框或流程图都不完整（依据 [NN/g Wireflows](https://www.nngroup.com/articles/wireflows/)）。

## 设计规格六要素与交接

依据 NN/g [Creating Design Specs for Development](https://www.nngroup.com/articles/creating-design-specs-for-development/)（2025）。规格在设计后期产出，前置条件是定义、方案比选与适用的验证已完成；规格过大就拆分，小而及时优于巨型文档。

| 要素 | 必写内容 |
| --- | --- |
| 交互流程 | 每个交互元素被操作后发生什么，逐元素写明 |
| 命名样式 / token | 引用命名样式与 token，不写孤立裸值 |
| 布局 | 栅格与断点行为 |
| 组件状态 | 全部适用状态与动效过渡，不只描述默认态 |
| 真实内容 | 真实数据与极端内容，不用占位灰块 |
| 无障碍标注 | Tab 顺序、可访问名称、alt 文本等显式标注 |

- 范围边界 → 规格单列范围内与范围外；范围外写明不做什么及原因，防止实现时顺手扩张。
- 交接必写信息（综合 NN/g 与 Figma 交接实践提炼，非联合标准）→ 逐元素行为、全部组件状态、断点规则、token 与组件引用、空/错/超长内容处理、无障碍要求、范围外明示、与既有模式的差异点及理由。
- 同步规则 → 设计更新必须记录并通知接收方；截图与设计文件不一致是实现走样的常见来源，以设计文件为准。
- 承载格式 → 用[交付与检查](delivery-and-review.md)的模块交互契约与组件行为契约；本文只规定内容构成，不另立模板。

## 模型适用边界

引用这些模型时连同其边界一起引用，不把任何一个当作完整答案。

| 模型 | 取用什么 | 边界与批评 |
| --- | --- | --- |
| ISO 9241-210 | 四活动骨架、评估驱动迭代、可验收的退出条件 | 抽象，不提供具体方法；对敏捷节奏下如何切分迭代无指导 |
| Double Diamond | 发散收敛节奏、回退合法性 | 止步于小规模交付、缺上线与持续运营（业界批评，官方亦有公开反思）；不是操作手册，阶段内方法需自选 |
| 设计思维（d.school / NN/g 六阶段） | 问题重框、可从任意模式进入的非线性 | 易工作坊化、群体思维；d.school 已公开反对把五步当唯一标准流程 |
| Design Sprint | 独立草图、结构化决策、启动前置条件清单 | 前置条件严格（Decider 在场、挑战够窄、约到真实用户）；5 名用户访谈找模式，不是统计证明；不适合小改进 |
| Lean UX / 持续发现与交付 | 假设绑定可测信号、未验证不进交付 | 最小化文档在强合规环境受批评；“双轨”易被误读为两个团队，Cagan 已弃用该词 |

共同盲区是止步于交付。本 Skill 以验证阶段覆盖空、错误与极端状态，并要求验收含上线后可观察结果，补齐该盲区（本 Skill 扩展）。
