# 状态与业务流程

目录：数据状态、反馈、权限与范围、并发、长任务、审批发布、通知、无障碍。除文内标注的 Cloudscape 依据外，任务恢复、授权变化和业务流程为本 Skill 的后台扩展规则。

## 数据状态必须可区分

适用于相应数据请求或变化存在的页面；各区块可以独立处理，不把局部异常升级为全页不可用。

| 状态 | 呈现与下一步 |
| --- | --- |
| 首次加载 | 用结构占位或合适的加载指示，不先闪现“暂无数据” |
| 成功且无记录 | 说明尚无对象；仅给当前角色实际可执行的创建、连接或返回路径 |
| 筛选无匹配 | 保留条件，支持修改或清除，不暗示底层集合为空 |
| 首次加载失败 | 说明获取失败并提供适当重试，不显示为零条数据 |
| 刷新中或刷新失败 | 可以保留仍可展示的旧数据，标明更新时间或过期状态；涉及授权变化时先按权限规则处理 |
| 局部失败 | 保留其余可用区域，定位失败部分；涉及整体计算的结果须标明不完整 |
| 无权限 | 解释允许披露的原因和可用路径，不泄露隐藏对象信息 |
| 对象删除或不可访问 | 说明无法继续并提供返回路径；不得展示过期的可执行操作 |
| 查询未完成或结果未知 | 展示待核实状态和查询方式，不伪装为成功或确定失败 |

依据：[空状态](https://cloudscape.design/patterns/general/empty-states/)区分无资源和无匹配；[加载与刷新](https://cloudscape.design/patterns/general/loading-and-refreshing/)区分初次加载和保留原数据的刷新。

## 反馈的范围和持续时间

- 字段错误放字段附近；局部依赖和风险放所在区域；跨页面任务结果放用户仍能找到的位置。
- 成功反馈可以是清晰的状态变化，不必每次弹出提示。错误和需要处理的结果不能仅靠一闪而过的消息。
- 反馈描述实际发生的事实：已保存、已提交审核、任务已创建、已停用分别代表不同结果。
- 明确执行中的范围，阻止同一动作重复触发；不因为一个按钮提交就把无关页面完全锁死。
- 有可计算进度时显示进度，没有时显示阶段或不定进度，不虚构百分比和完成时间。
- 重试只适用于可重试且结果明确的失败；网络超时可能已有副作用，先查询结果或使用可保证不重复的请求机制。

依据：[反馈机制](https://cloudscape.design/patterns/general/user-feedback/)根据上下文和进度是否可计算选择反馈。本 Skill 不把固定秒数直接当成所有后台的硬阈值。

## 权限、只读与范围变化

- 分别判断查看权限、操作权限和数据范围。无编辑权不必意味着无查看权；查看列表也不自动获得导出权。
- 长期无关且无法启用的动作可以隐藏；暂时缺少前置条件的动作可以禁用并解释；只读数据保持可读。
- 如权限申请是实际存在的流程，提供明确入口；没有申请路径时不放无效的“申请权限”按钮。
- 有必要的禁用原因不能只靠鼠标悬浮获取，键盘和触控用户也应能了解。
- 前端隐藏或禁用只是呈现方式，服务端仍需在每次请求校验权限与范围。
- 用户在操作中权限失效时停止不再允许的提交或展示。可保留允许保留的非敏感输入，不能用缓存继续暴露已无权查看的数据。
- 登录过期后尽量恢复原任务上下文；敏感表单是否可暂存由产品策略决定，不默认存入浏览器持久化存储。
- 切换组织、项目或环境后重新加载权限和数据；不可沿用上一范围的已选记录、详情内容或危险操作确认。

依据：[禁用与只读](https://cloudscape.design/patterns/general/disabled-and-read-only-states/)说明非交互状态和原因解释。授权校验与缓存处理为后台扩展。

## 多人编辑和数据过期

**条件必需**：同一对象可能被多人、外部同步或后台流程修改。

- 读取和提交之间发生变化时，检测并说明冲突；不能默认静默覆盖其他人的新值。
- 给出业务允许的恢复方式，如重新加载、对比差异、保留草稿再合并；强制覆盖只能在产品明确允许且有权限时提供。
- 重要状态动作在执行前重新确认对象当前状态；原列表中的“可操作”不是永久许可。
- 自动刷新不覆盖正在编辑的字段，避免重排行导致用户操作了另一对象。以稳定对象标识关联动作和选择。
- 用户看到旧数据时明确陈旧程度；关键决定需要新数据时提示刷新或重新验证，而不是对所有陈旧数据一律锁屏。

## 异步任务、取消与重试

**条件必需**：长时间执行、离页后继续或无法即时确认结果。任务入口可以是现有详情、状态面板或任务列表，按规模选择，不默认新建完整任务中心。

| 任务阶段 | 交互约定 |
| --- | --- |
| 提交中 | 阻止重复提交，不显示业务已完成 |
| 已受理或排队 | 给出任务身份与结果入口；有排队信息才显示位置或预计时间 |
| 运行中 | 展示可信阶段或进度，说明能否离开、能否取消 |
| 请求取消 | 明确取消请求待处理，不能立即声称工作已停止 |
| 成功 | 展示结果和下一步，更新相关对象真实状态 |
| 部分完成 | 展示各项结果，说明是否已有不可撤销的副作用 |
| 失败 | 定位原因和实际可行的修正、查询或重试方式 |
| 结果未知 | 查询任务或对象状态；禁止将未知结果直接当作失败重新创建 |

- 关闭弹窗或页面仅关闭视图，除非产品明确如此设计，不自动取消后台任务。
- 取消操作只有执行端支持时才出现；说明已经完成部分是否保留。取消失败给出实际状态。
- 重试区分“重试未完成部分”和“重新执行全部”，提供明确范围。可能重复扣费、发送或写入的操作先解决重复执行语义。
- 对需要离页后查结果的任务，刷新或重新进入仍能找到状态；不允许只存在于即将消失的提示框。
- 报告任务中的部分失败和跳过，不把 90 项成功、10 项失败汇总成一句“成功”。

## 审批、发布和回滚

只有明确的审核责任或生效流程才引入这些能力。定义角色和状态，不把流程塞进任意编辑状态字段。

- 提交前让用户知道提交对象、版本、范围和必要后果；提交审核与正式生效分别反馈。
- 待审时说明能否修改、撤回或重新提交；拒绝后说明原因和可修改范围，审批意见按业务需要必填。
- 审批行为绑定被查看的版本；内容变化后不能直接批准未审阅的新版本。
- 发布前按风险核对变更和影响；发布中、成功、失败或部分生效分别显示。
- 定时生效明确时区、计划时间、执行状态以及变更计划的条件。
- 回滚只有存在可恢复版本且业务允许时提供；展示目标版本和可能影响。回滚不是删除历史，也不保证能撤销外部副作用。

## 通知与操作历史

- 原位反馈能完成任务时无需通知中心。确需离页后处理的事件提供持久可访问入口及正确的对象链接。
- 区分信息、待处理项和故障；已读不等于已处理，失败重试不等于任务完成。
- 长任务状态不反复刷屏；有重要变化才产生相应反馈。外部邮件或消息通知按已确定的业务需求建设。
- 需要追溯的关键变更记录谁、何时、对何对象、做了什么、结果如何；必要时显示变更前后，遮蔽敏感值。
- 不依据泛化的“合规需要”擅自制定保留期限、审批层数或全量记录策略。

## 可访问性与响应式

下列为页面底线；具体控件的键盘、焦点与浮层差异按 [组件交互设计语言](component-interaction-language.md) 判断，不把模态规则套到所有浮层。

- 核心任务能够使用键盘完成，焦点顺序与操作逻辑一致，焦点可见；图标按钮有可理解的名称。
- 模态打开时焦点进入，关闭后返回合理触发位置；模态内焦点不误入背景。Esc 和关闭按钮遵守同一未保存规则。
- 重要状态和错误可被辅助技术感知，同时避免每次刷新都抢焦点或重复播报。
- 颜色不单独承载状态，拖拽和悬浮不成为关键操作的唯一方式。
- 窄屏或缩放时保持必要信息和操作可达；可用横向滚动或摘要加详情，不为了塞下表格把文字无限缩小。
- 是否支持完整手机操作由任务确定；明确支持范围，不能把未经验证的适配写成已完成的无障碍合规声明。

焦点规则可核验 [WAI-ARIA 模态模式](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)。这不是对项目已符合某等级标准的认证。
